Supabase's growth engine was never a campaign. It was legibility. From early on, the docs read like they were written for someone who wanted to succeed in one sitting, and the quickstart actually worked. That was good DX in the human era. In the agent era it turned into something stronger: a surface that models reproduce faithfully because it's unambiguous and it runs.

## The move

When a developer, or increasingly a PM with an agent, says "add auth and a database," the tool that gets chosen is the one the agent can wire up without guessing. Supabase leaned into being that tool. Standard Postgres underneath, so a model already knows the mental model. Clean client libraries. And an MCP server that lets an agent create tables, manage policies, and act inside the project directly.

That last part matters most. An agent using the MCP server isn't writing code it hopes is correct against a library it half-remembers. It's calling operations that either work or return an error it can read.

## Why it works

"The open-source Firebase" gave the model a clean handle to retrieve. "Just Postgres" meant the model's existing knowledge transfers instead of fighting a proprietary abstraction. And the relentless investment in examples meant the internet filled up with correct usage the model could learn from. Every faithful tutorial became Supabase's distribution.

What the rest of us can take from it: the agent-era default goes to whichever option in your category is the most legible and the most actionable, and to the tools agents can do things through rather than merely reference.
