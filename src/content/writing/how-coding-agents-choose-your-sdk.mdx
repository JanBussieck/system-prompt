Every SDK decision used to begin with a human on your homepage. A growing share of them now begin with a coding agent, mid-task, deciding which library to reach for, and the human may never see the runner-up. If you want to be the default, you have to understand how that choice gets made. It isn't one decision. It's four layers, and each is something you can win or lose independently.

## Layer 1: the training-data prior

Before an agent reads anything, it already has opinions. If your library existed, was popular, and was well documented before the model's training cutoff, the model "knows" you and will suggest you unprompted. This is the layer everyone feels and almost no one can move, because you can't retrain someone else's model. It's also the slowest and least fair of the four, which is why the other three matter so much.

## Layer 2: runtime docs and retrieval

Most agents don't run on memory alone. They fetch. An `llms.txt`, a structured reference, a docs site the agent can read, a retrieval index: these are what the model consults *at decision time*, and unlike the training prior, you can change them this quarter. A newer library with clean, machine-legible docs can leapfrog an incumbent that's coasting on Layer 1, because at the moment of choice the agent is reading current reality rather than stale weights.

## Layer 3: tools it can act through

There's a categorical difference between a library an agent *imports and hopes it wrote correctly* and a capability it can *call* directly. An MCP server or a first-class CLI moves you from the first category to the second. When an agent can create the resource, run the migration, or wire the config by calling your tool instead of hand-writing code against it, you stop being one option among many.

## Layer 4: does the happy path hold

Getting picked is worthless if the first attempt fails. When an agent chooses you and the quickstart doesn't run, or the error is inscrutable, or the API it "remembered" was renamed two versions ago, it backs out and reaches for whatever feels safer next time. The failure gets blamed on you. First-try success and error messages an agent can recover from are a selection lever, not a DX nicety.

## Why most teams lose the layers they could win

The pattern across the industry is that teams pour effort into Layer 1, hoping they made it into the training data, and quietly ignore Layers 2 through 4, the ones they actually control. That's the whole opening. A smaller tool with an `llms.txt`, an MCP server, runnable examples, and recoverable error messages routinely beats a dominant player resting on brand recognition the model happened to absorb.

Your position in the agent's decision is mostly decided by your docs, your types, your tooling, and your error surface, all of which live in engineering rather than in a campaign. Audit each layer honestly. Layer 1 you inherit. The other three you can start winning today, and almost everyone is leaving them alone.
