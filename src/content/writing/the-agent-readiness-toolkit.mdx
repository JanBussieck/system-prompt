If [the agent's pick happens in four layers](/writing/how-coding-agents-choose-your-sdk), the good news is you don't have to build the machinery for each one yourself. A small ecosystem has appeared to help dev tools become legible, actionable, and measurable to coding agents. Here's the practitioner's map: what each thing is good for, and where it stops.

## Make yourself legible

`llms.txt` is the emerging convention for a machine-readable index of your docs, pointing agents at the canonical, clean version of your reference. It's the cheapest high-leverage move on Layer 2, and it's just a file. Ship one.

Docs platforms have started to speak agent. Mintlify auto-generates an `llms.txt`, can spin up an MCP server from your docs, and reports AI-referral analytics. If your docs already live there, a lot of Layer 2 is a config toggle away.

## Serve your docs to agents at runtime

Context7 serves up-to-date, version-correct library docs to coding agents over MCP, so the model works against current reality instead of its stale training prior. Being well represented there is a direct hedge against a bad Layer 1.

## Let agents *act*, not just read

MCP, the Model Context Protocol, is the standard that turns your tool into something an agent can call. This is the Layer 3 move, and it's the one most likely to change your selection share outright.

SDK generators like Speakeasy and Stainless produce typed, idiomatic SDKs from an OpenAPI spec, and increasingly an MCP server alongside them. Useful when your surface is an API and you want agent-ready clients without hand-maintaining six languages.

## Measure, benchmark, and score

Sapient is the first platform built specifically for this. It tracks your visibility across coding agents (Claude Code, Codex, Cursor, and more), runs a "Devtool Arena" leaderboard on agent-readiness, and audits docs. Strong for *am I visible and mentioned*, lighter on *does the agent ship working code with me*.

Auth0's Agent Experience Score is less a product than a useful public rubric for how agent-friendly a product is. Worth reading as a checklist even if you never adopt it.

The research benchmarks, MCP-Bench and MCPToolBench++, are academic evaluations of whether agents use MCP tools correctly. They're not about your SDK, but the grading methodology is what a serious internal eval should borrow.

## Where the toolkit runs out

Notice what's well covered and what isn't. Legibility (llms.txt, docs) and visibility (Sapient) have tools. Usage success does not. Whether the agent actually produces working code with your SDK on the first try, and which specific change caused the lift, is still mostly a build-it-yourself eval: a sandbox, a task battery across real agents, and automated grading. That gap is also where the honest answer to "did it work" lives.

If you'd rather not stand up that harness yourself, that's the thing we do, and you can read about it on the [Agent Readiness Audit](/audit) page. Either way, start with `llms.txt` this week, ship an MCP server this quarter, and measure before and after. The tools exist. Most teams just haven't picked them up.
